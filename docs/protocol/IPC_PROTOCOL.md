# IPC Protocol — Version 1 Baseline

**Status:** Contract proposal. Preferred transport is gRPC with Protocol Buffers over the private Compose network; implementation and transport-security details are finalized in M0.3.

## 1. Purpose

The IPC Gateway provides a narrow, versioned service contract between Web, the server Core, and plugin backends. In the initial architecture the Gateway and Core are modules in the same `postflowx-server` process; the Gateway is still a logical trust/validation boundary. The preferred transport between containers is gRPC with Protocol Buffers over the private Compose network, not published to the host. Use request/response RPCs; add streaming only when a concrete use case requires it. Finalize authentication, deadlines, health checks, compatibility and generated-code workflow in M0.3.

## 2. Transport requirements

- Private internal network only.
- Authenticated service identity; use transport authentication appropriate to the selected transport.
- Explicit request and response schemas defined in Protocol Buffers for gRPC methods.
- Request deadlines and bounded payload sizes.
- Correlation IDs for tracing.
- Health endpoint separate from ordinary business routes.
- No direct plugin-to-database path.
- No public unauthenticated IPC endpoint.
- No transport-specific assumptions in business modules.

## 3. Envelope

Every operation uses a versioned typed request/response contract. The following JSON is a conceptual illustration of the logical fields, not a requirement to serialize this envelope as JSON on the wire; the concrete `.proto` messages and RPC methods are defined during M0.3:

```json
{
  "protocol_version": "1",
  "request_id": "uuid",
  "source_service": "plugin.instagram",
  "operation": "publishing.create",
  "deadline": "2026-10-19T12:00:05Z",
  "actor_context": {
    "kind": "user",
    "id": "internal-user-id"
  },
  "payload": {}
}
```

Rules:

- `request_id` is generated by the caller and unique per attempt.
- `source_service` is authenticated independently; the string alone is not identity.
- `operation` must be on the route allowlist.
- `deadline` is bounded by server policy; callers cannot request infinite execution.
- `actor_context` is accepted only when cryptographically/transport-bound or minted/validated through the Core authentication contract. The Web BFF must not turn a client-supplied user ID into trusted identity; plugin-supplied actor IDs are also untrusted input.
- Payloads are validated against the operation schema.
- Unknown fields are rejected for security-sensitive operations unless a schema explicitly allows extension fields.

Conceptual responses use the following logical shape (the actual gRPC response is defined in Protocol Buffers):

```json
{
  "protocol_version": "1",
  "request_id": "same-request-id",
  "status": "ok",
  "result": {}
}
```

or:

```json
{
  "protocol_version": "1",
  "request_id": "same-request-id",
  "status": "error",
  "error": {
    "code": "FORBIDDEN",
    "message": "Operation is not permitted",
    "retryable": false
  }
}
```

Do not return stack traces, SQL errors, secrets or internal filesystem paths to untrusted callers.

## 4. Initial error codes

- `INVALID_ENVELOPE` — malformed envelope.
- `UNSUPPORTED_PROTOCOL` — unsupported protocol version.
- `UNAUTHENTICATED` — service identity could not be authenticated.
- `FORBIDDEN` — identity authenticated but capability/ownership denied.
- `NOT_FOUND` — resource absent or intentionally hidden from caller.
- `VALIDATION_ERROR` — payload fails schema validation.
- `CONFLICT` — state/version conflict.
- `RATE_LIMITED` — rate or concurrency limit exceeded.
- `DEADLINE_EXCEEDED` — request deadline expired.
- `UNAVAILABLE` — dependency not ready or temporarily unavailable.
- `INTERNAL_ERROR` — unexpected server failure; no sensitive details included.

Retryability is operation-specific. Never automatically retry a non-idempotent publish operation merely because the IPC request timed out.

## 5. Idempotency and retries

- Read-only operations may be retried within deadline policy.
- Mutating Core operations accept an idempotency key where duplicate execution would be harmful.
- A timed-out request may have completed. The caller should query operation/job state using the request or idempotency ID before repeating it.
- External publishing operations require their own attempt IDs and `OUTCOME_UNKNOWN` handling.
- The Gateway must not silently replay non-idempotent calls after reconnect.

## 6. Identity and authorization

- Each service has a distinct identity. The Web BFF authenticates as a service to the Gateway; a browser user identity is conveyed only through the agreed Core-validated session/context mechanism.
- Core is the authorization authority for application data.
- Plugin capability is the intersection of manifest-requested capabilities, administrator grants, user-level grants and current resource ownership.
- Admin operations are not reachable by plugin identities unless a narrowly defined capability explicitly permits an action.
- Gateway authentication protects service-to-service access; Core authorization protects data and business operations. Both are required.

## 7. Initial operation groups

- `health.read` — service health; limited to monitoring/admin contexts.
- `users.*` — Core-only/admin-authorized user operations.
- `plugins.registry.read` — list installed plugins and permitted metadata.
- `plugin.storage.*` — namespaced storage operations, always owner-scoped.
- `secrets.use` — use a secret for an approved integration operation; do not return plaintext secret by default.
- `media.create`, `media.read`, `media.delete` — authorized media metadata/content operations.
- `publishing.create`, `publishing.read`, `publishing.cancel`, `publishing.retry` — authorized job operations.
- `audit.append` — controlled event append; plugin cannot write arbitrary actor identities or forge system events.

Exact schemas for each operation must be defined alongside implementation and contract tests. This document defines principles, not permission to implement an unrestricted generic RPC endpoint.

## 8. Health and readiness

Health checks must distinguish:

- process alive,
- service ready to accept work,
- dependencies healthy,
- application degraded.

Use a bounded response with status, service ID, protocol version, uptime and dependency summary. Do not leak secrets or detailed infrastructure data to public clients.

## 9. Versioning

- Protocol version changes when compatibility breaks.
- Additive changes are allowed only if old clients safely ignore them and validators permit them.
- Unknown major versions fail closed.
- Each service declares supported protocol range.
- CI runs contract tests for every service pair.
- Deployment release manifests pin compatible service versions.
